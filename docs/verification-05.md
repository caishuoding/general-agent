# 任务 05：Mem0 明确保存与查看

实现范围：真实浏览器 `/runs` 与同步 `/messages` 入口的明确保存、正式记忆和来源查看、真实操作状态、预算与重试恢复，以及锁定版本的 Mem0 PostgreSQL 适配。未提前实现任务 06–09 的相关召回、编辑删除或候选确认。

## 用户行为与公开接口

- 当前输入以 `请记住：具体事实`、`记住具体事实`、`请帮我记住具体事实` 等独立句首形式明确要求时直接保存。普通事实、否定、转述中的命令词、写作/假设情境不成为保存授权；“记住这个”、附件引用或多个不清楚的目标返回澄清。事实内部普通引号可以保留，例如 `我的昵称是"小林"`。
- 分号可分开明确保存与回答请求；保存成功后继续回答。仅保存时由后端根据正式提交生成回执，不再付费调用模型声称成功。附件供参考前缀不影响同条输入的直接事实。
- `GET /api/memories` 返回事实、状态、Mem0 标识、原会话、原用户消息、时间及安全错误；完成条目再次经真实 Mem0 `get` 核验。管理页可跳回原消息。失败状态不冒充已保存。
- 助手消息与 SSE 快照增加 `memory_action` 和 `budget_pause`。记忆动作和回答尝试分别持久化，因此“保存完成、回答失败/暂停”会同时如实显示。停止不会撤销已完成的记忆。
- `POST .../messages/{id}/resume` 恢复同一暂停尝试，不增加用户消息或从头重做已完成保存。先用已有预算 approve 接口批准当前 `pause_id`，或补价后直接恢复；取消可通过 stop 或预算 cancel。初始 202 是受理回执，不再缓存成最终业务结果。

## Mem0 与持久化决策

精确锁定 **mem0ai 1.0.11**，真实 OSS `Memory` CRUD 与官方 PGVector；未使用托管 MemoryClient。该版本并非最新，选择 1.x 是为了当前已批准文本的明确 CRUD 避免引入 2.x 实体提取与额外衍生集合生命周期；升级必须重新跑契约，适配器会拒绝其他版本。

自定义兼容层 `mem0_adapter.py` 覆盖初始化、关闭、重置并注入 PostgreSQL 历史与显式预算嵌入器，完全不构造默认 SQLite 或默认云模型客户端。`mem0_history` 由 SQL 迁移管理；每次历史读写独立短连接，兼容 SDK 内部线程池。所选 SDK 实际契约为 add_history/get_history/reset/close；1.0.11 不存在较新版的最近消息或批量历史路径，未宣称实现那些不存在的方法。

- `Memory.add(..., infer=False)` 只接收已批准事实字符串，一次嵌入、零 LLM。默认推断模型适配明确拒绝未批准的推断路径。
- 每次 SDK 会话创建操作专属 embedder，绑定不可变 `OperationContext`，不依赖 ContextVar 或修改共享实例；所有嵌入通过现有 BoundCalls，先记 usage 再返回向量。
- 1.0.11 PGVector 返回 cosine distance；局部子类转为 `1-distance`，保持 Mem0 阈值的相似度语义。
- SDK 更新默认丢失自定义 metadata；局部 update 先合并原来源并保留原身份字段，真实 SDK 契约验证了该差异。产品编辑仍由任务 07 实现。
- `close` 幂等关闭实际向量连接池和历史适配；`reset` 不回退 SQLite。reset 是内部维护契约，未暴露清空用户数据接口。
- 默认 SDK delete 留存历史正文，契约通过显式历史 purge 验证清除；产品删除和旧来源抑制由任务 09 实现。
- 首次导入前关闭 `MEM0_TELEMETRY`；禁用含事实正文的 SDK 日志。`.local/mem0-runtime/` 仅是 SDK 导入要求的辅助目录；正式记忆、历史、来源、操作、向量和用量均在 PostgreSQL。

`Dockerfile.postgres` 保持原 PostgreSQL 17 Alpine 镜像摘要，编译固定 pgvector 0.8.7，下载源 SHA256 `cac0b10c360f05b2d521200105ba3697e773d4cd3731f5a915a7e37ebe0bea85`。正式 Dockerfile 已构建成功，镜像 `general-agent-postgres:17-vector0.8.7`；Compose 保留原卷与端口，启动脚本使用 `--build`。Alpine 构建工具包随固定基础所指软件源安装，未宣称逐包可复现构建。主库镜像切换由最终集成维护完成，本票未重启或修改用户数据库。

## 编排、预算与后续接缝

`ChatExecution` 负责从当前用户输入识别批准、预留真实首个调用并执行批准动作；`StreamingChat` 保留线程、消息尝试、SSE、停止与重试。同步入口也使用相同 execution 模块，并先提交用户消息再执行，云端等待期间不持有会话行锁。

- `execution.reserve_first(content, settings, operation, user_id=None)`：普通聊天预留 chat；保存预留 embedding；重试已有动作先对账，确实需要嵌入时才在工作步骤内预留。不能提前预留最终 chat 后再执行 embedding。
- `execution.prepare(conversation_id,user_id,content,operation,reserved)`：返回确定本地回执，或 `None` 继续回答；已完成的事实不重复添加。
- `execution.chat_reservation(content,reserved)`：普通聊天可用最初预留，保存所用嵌入 ID 不可挪作 chat。
- `execution.scope` 与消息中的模型/嵌入版本绑定初始批准和暂停恢复；配置改变后旧批准不能挪用。异步受理通过持久化 message.operation_id 防重，不缓存初始 202 为最终结果。
- 消息 `paused` 保留 `budget_pause`，仍占用当前会话执行位置。停止或取消撤销操作许可；已经发出的请求仍保存能取得的用量。应用重启保留 paused，生成中答案标失败、saving 动作标为待核对失败；重试不会假定未提交。
- 资料模块可在 prepare 后、实际 chat 调用前加入带出处的材料；不能把资料或旧消息当本次动作授权。任务 10 将合并其 AttachmentService 材料接入；不新建第二套执行器。

`MemoryService.save` 的业务动作 ID 为原用户消息稳定派生值；会话+消息来源、批准正文和操作状态先持久化，再调用 Mem0。SDK 向量与历史独立提交，应用使用动作级锁以及受信任 metadata.action_id 先对账：已存在向量修复缺失历史，不再次 add。记忆成功但后续回答失败，重试只发出新的回答调用。

后续 06 召回必须只采用 memory_actions 中完整成功的有效条目，不能直接把 SDK 中部分提交孤儿视为已生效事实。后续 09/15 删除应清理 action 正文、内部历史、向量与相关幂等结果，并按原计划做旧来源抑制；操作 ID 和来源关系已持久化。更新与删除的业务授权不能仅依据 SDK metadata。
