# 任务 07：修改记忆与明确更正

实现管理页按条目编辑，以及同步聊天和真实浏览器 `/runs` 的明确更正。保留任务 06 的相关召回、预算检查点及任务 10 / 12 的会话附件、图片能力和引用。没有提前实现候选确认或删除产品接口。

## 用户可见行为与接口

- `PUT /api/memories/{action_id}` 接收 `fact`、`expected_version`，使用 `X-Operation-ID` 防止同一请求重放。条目版本已变化、有另一项未完成更正或正文为空时不会覆盖；操作标识不能挪到不同正文、条目或配置。
- 管理页提供“编辑记忆”“保存更正”“重试更正”，新事实完整同步成功才显示为正式当前事实。提交期间不保留“已保存旧值”的成功提示；刷新后也可看到真实未完成状态。
- 聊天支持独立明确句式：`更正记忆：完整旧事实 => 新事实`、`请把记忆中的“完整旧事实”改为“新事实”`，或 `更正记忆 <管理页记忆标识>：新事实`。更正、修改、更新可作为命令词。目标必须是一个明确标识或唯一完整旧事实；歧义先返回澄清，不重复确认已经明确的同一指令。当前不使用 LLM 猜测自由句式的修改对象，也不自动建立任务 08 的候选变更。
- 当前用户消息是唯一动作授权来源。普通陈述、转述、否定、历史材料、附件和虚构语境中的词句不会自动更正。完成的本地确定回执为“已更正长期记忆”，不依赖模型声称已更新。
- `GET /api/memories` 增加每条记忆的 `updates` 来源与状态；原会话、原消息与正式 Mem0 标识不变，每个聊天更正另存其新会话和原用户消息。管理页可以分别跳回原消息和更正消息，管理页编辑明确标为“管理页更正”。
- 助手消息增加 `memory_update`，独立表达更正状态；同步失败、预算暂停和停止时，消息与记忆页不显示虚假成功。`POST /api/memory-updates/{id}/retry` 保留原目标及来源，作为新的可计量尝试。

## 稳定身份、版本和真实 Mem0 同步

接受明确更正时，在事务中创建 `memory_updates` 并把原 `memory_actions` 标为 pending，同时将版本递增一次。旧条目从任务 06 的正式候选筛选中立即退出；失败或停止后不回退为旧值可召回状态。重复请求与重试复用同一更新记录及目标版本，不再次递增版本，也不创建第二条冲突的有效记忆。

同一个记忆动作的更新使用动作级数据库锁串行处理。业务来源关系保存在 PostgreSQL；正式 Mem0 `memory_id` 保持不变，通过锁定版本的真实 `Memory.update` 同步新事实。现有适配器合并原 metadata、保留个人身份与原来源，再添加本次 `correction_id`；不调用默认自动推断 LLM。

SDK 的向量和历史分别提交。重试先读取正式向量：如果内容和 `correction_id` 已匹配本次更正，就只核对或修复内部历史，不再次嵌入。历史必须匹配旧值、新值以及当前 SDK `updated_at`；不能用更早一次相同旧新值组合冒充本次已提交。两者完整核对后，才在同一业务事务中将更新记录和正式条目设为 complete 并启用新事实。

已有相关召回检查点只保存标识和版本。接受更正后的新版本立即使旧检查点失效；暂停回答恢复会重新核验并剔除旧条目，不再次嵌入、不发送旧值。之后的新会话重新查询可取得新正式值。已经开始的云端请求不会被追溯撤回。

## 预算、停止、重试与配置

更正先停用旧事实，再在真实嵌入步骤检查预算，因此预算暂停期间也不会把旧值继续当当前事实。每次真实嵌入使用现有调用网关、个人嵌入配置和用量记录；单纯更正无额外聊天模型调用。

管理页暂停通过统一预算弹窗恢复同一操作；聊天暂停沿原消息 `/resume` 恢复，应用重启保留 pending 状态。停止冻结回答并撤销后续调用许可，已发出的嵌入保留实际返回用量，尚未写入的向量不会继续提交。失败或停止后的显式重试保留原更正 ID、版本和来源，已部分提交的向量先核对恢复。

每次批准绑定原条目、正文、版本和嵌入配置修订；配置变更不能挪用旧批准。新尝试可以使用新配置，但须先通过嵌入验证。启动中断的 saving 更正标为 failed，旧事实仍停用，后续按原记录核对。

## 数据位置及后续删除合同

迁移 `008_memory_correction.sql` 在同一 PostgreSQL 增加：

| 记录 | 内容与后续清理责任 |
| --- | --- |
| `memory_updates` | 旧正文 `previous_fact`、批准新正文 `fact`、稳定动作 ID、目标版本、真实状态和来源。任务 09 / 15 删除记忆时必须清理这些正文；不能只清理 `memory_actions.fact`。 |
| `memory_update_operations` | 每次原操作及显式重试的 `update_id -> operation_id` 关联，不含正文。删除时据此调用既有预算失效逻辑，清除所有关联 `cloud_operations.result` 缓存及批准，不能只处理更新记录上的最后 `operation_id`。 |
| 更正的聊天来源 | `source_conversation_id`、`source_message_id` 与原记忆来源分别保存。任务 15 列出关联记忆时，应合并原来源和这些更正来源；保留记忆时按来源删除规则处理引用，而不是忽略这些外键。 |
| 正式 SDK 与内部历史 | 同一 Mem0 向量实体可能含当前正文，`mem0_history` 包含旧新正文。记忆删除需清除向量、内部历史和上述业务更正正文；SDK metadata 中的原来源及 `correction_id` 仅作核对信息，业务记录决定授权。 |

原始聊天和助手回执是独立来源记录；删除记忆本身不删除原聊天。防止从旧来源恢复仍由任务 09 实现，本文没有宣称已经完成该产品行为。任务 06 的召回检查点不复制正文，正式状态、版本或实体失效后就不会继续提供条目。
