# 任务 12：PNG/JPEG 图片上传与视觉问答

## 已实现行为

- 复用会话附件上传、原文件保存、消息关联、处理状态和原文件下载接口。PNG、JPG、JPEG 扩展名大小写均支持；文件实际格式由固定 Pillow 12.3.0 验证，不相信上传 MIME。先 `verify` 再重开 `load`，完整性校验或解码失败显示真实失败，不把文件标为可用。
- PNG 与 JPEG 原字节通过 OpenAI 兼容的 `image_url` data URI 发送；实际 MIME 来自本机验证。没有转为假文字摘要、OCR、静默压缩或漏发选中的图片。`ModelMessage` / `TextPart` / `ImagePart` 明确区分文字和多模态数组，普通文本协议保留。
- 当前消息选中的图片会在真正需要模型回答时读取；原会话可勾选旧图片、指定文件名，或明确“看看这张图片”“图片里写了什么”等继续追问。未随消息发送的上传不会被自动读入；普通聊天、泛泛询问图片功能和明确拒绝读图不自动携带旧图片。图片范围超过五张时明确要求缩小选择，不能静默漏图。
- 只有实际生成图片材料时才核对 `capability_checks` 中当前配置 revision 的 `image=passed`。未通过或变更模型/地址/密钥后旧验证失效，保留失败回答及原附件关系，设置中验证图片能力后可重试原回答。图在会话中存在本身不强制普通聊天经过视觉门槛。
- 明确“请记住：具体事实”先经共同 `ChatExecution.prepare` 执行；仅保存的本地回执不读取图片，即使同条消息选了图片也不会强制视觉能力或把图片内容当作记忆授权。实际视觉回答再准备相关已批准记忆，两类材料均不成为新的动作授权。
- 图片使用 `attachment_chunks` 中一个持久来源记录分配全局 A 来源键，位置恒为“图片本身”。摘录明确说明未执行 OCR 或预先文字提取；不会制造图片页码、段落或假摘录。后端仍仅接受本轮真实提供且仍属当前会话的引用，模型编造来源显示未核验。引用有效证明来源身份，不保证模型结论正确。
- UI 已支持图片选择和上传，展示真实格式、尺寸、处理错误与视觉配置提示。文档中的图表或截图可单独上传。原会话刷新仍保留附件和出处，新会话需要重新上传；同图在另一会话重传具有独立标识和出处。

## 限制与持久化

每条消息最多五个附件、每文件最多 20,000,000 字节，继续由统一上传与消息绑定接口执行。图片校验额外限制为最多 4,000 万像素，Pillow 解压炸弹警告作为失败；多帧 PNG 明确拒绝，需要导出要分析的帧。没有声称理解所有动画帧、文档内嵌图、复杂图表或扫描 PDF，也没有新增 OCR。

原文件仍保存在 `APP_DATA_DIR/attachments/<UUID>`，处理状态、真实格式/尺寸、消息关系和引用在同一 PostgreSQL 业务库。新增迁移 `013_images.sql` 只增加可空 `attachments.image_metadata`，已有文本附件按空值保持原行为。图片占位来源不能进入文字片段检索；真正读图必须附实际图片字节。

数据 URI 增加请求体体积。符合本机上传上限不表示任意供应商接受五张大图片；供应商拒绝会显示 HTTP 失败、保留已取得的 usage，并允许用户调整输入或重试。没有进行真实模型兼容性承诺。

## 共同执行与后续接缝

- `AttachmentService.prepare(..., settings=...)` 返回 `AttachmentContext`，其 `messages` 为明确类型 `list[ModelMessage]`；`image_sources` 只做会话、消息和能力限定的本地来源选择。后续图片提取需复用此归属及能力边界，不能直接加载跨会话文件。
- 同步与流式都先完成已批准动作，再本地准备附件及视觉检查，然后通过 `prepare_answer` 准备相关记忆，最后使用原有统一 `BoundCalls.complete/stream`。视觉检查失败时取消尚未发出的预留，不发图片或不必要的召回请求。
- 停止、预算暂停、配置版本检查、单次批准、失败重试及幂等操作仍由原执行器负责，没有第二套视觉执行器。实际视觉请求与能力检查分别计量；服务拒绝仍记录可取得的输入/总 token，缺失字段保持未知。停止后正文冻结，但已发请求返回的尾部 usage 仍记录。
- 图片引用的 `attachment_id` 与 `attachment_chunks` 来源记录应和其他附件一起由后续来源删除流程清理，不能只删原文件却保留当前可用图片来源。
