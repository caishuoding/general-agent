## 用户行为

“请全文总结资料”“完整总结这份文档”“比较 Alpha.pdf 和 Beta.txt 的完整资料”等当前用户明确请求进入全文流程。普通具体问题继续使用任务 10 的相关片段检索，否定或询问“总结是什么意思”不启动全文处理。范围优先本条消息选定的文件，其次当前会话内已发送的具名文件，否则使用本条消息之前已发送的文件。新会话不能取得其他会话资料。

全文处理读取全部可提取文字，包含末尾，先每四个原始片段形成分段结果，再每四份结果逐层汇总，直到剩余不超过四份。每份中间结果最多 3000 字符；最终输入不夹带冗长历史聊天。全部原文都经过实际模型请求，不以检索的十二个片段冒充全文。最终结果须包含每份可读文件的合法来源，来源键由后端持久身份构成，文件正文内的伪标记不能扩大允许范围。

部分 PDF/DOCX 的页或结构缺口、图像和复杂排版限制继续显示；明确具名但失败的当前会话上传列入缺口。图片在文字总结中只说明未读取，不把占位文字或图片字节作为已提取文字。不含任何可读文字的范围明确失败。最终回答附后端生成的逐文件范围说明；“已完成”表示所有计划中的可处理文字步骤完成，不表示解析缺口已被补齐。

聊天和同步接口共享原动作执行与预算网关。界面显示真实完成步骤数、全文总结或资料比较、范围、等待预算、停止或失败状态，刷新和重启后保留。一次预算批准仅放行下一次真实请求，每个分段、递归汇总和最终回答单独计量。停止冻结可见内容和进度；已发出的服务请求仍可返回用量和完成检查点，用户显式重试时复用已完成结果。旧请求仍未收尾时阻止重叠调用。

启动恢复只释放实际中断回答所关联的运行步骤和最终调用占位，不修改另一条已暂停任务的进度或批准挑战。杀掉实际应用进程后，已持久完成分段仍可复用；进程中断时尚未确认结果的请求保留未知用量，显式重试可能需要再次发送该未完成步骤。不会把无法确认的响应声称为已完成，也不自动重试。

## 模块、存储与后续清理合同

`summary.py` 的 `DocumentSummary.prepare(...)` 返回 `SummaryPreparation` 或 `None`，只提供原聊天执行器所需的材料和检查点。`step`、`reserve_final`、`finish` 分别约束单个有据结果、最后一次预算请求及完整输出验证。`calls.py` 的非流式调用增加可选 `assistant_message_id`，让分段调用与原回答关联。没有新增执行器、服务连接、依赖、密钥或启动参数。

`014_document_summary.sql` 新增：

- `document_jobs`：按原用户消息与聊天配置版本唯一，包含会话、来源及召回上下文指纹、附件 ID 数组、逐文件范围、总步骤数、最终调用与完整回答缓存。
- `document_steps`：按任务、层级和序号唯一，包含运行/完成/失败状态、实际调用 ID 与分段正文。任务删除时级联删除。
- `messages.document_job_id` 与 `document_progress`：回答尝试关联及当时可见进度。任务删除时外键置空；进度 JSON 需要同时主动清理。

这些中间结果和最终缓存都是派生正文，不能按纯日志处理。任务 15 删除文件或会话时，应先取消关联尝试和后续预算批准，按 `document_jobs.conversation_id` 或 `attachment_ids` 查找任务，删除任务及级联分段，并清理相关消息的进度、引用和其他应删正文；内存中的工作步骤必须重新核验删除状态，不能重建缓存。仅删除原始文件不会完成资料清理。保留未涉删除的其他会话与上传。

最终结果可能结合长期记忆；任务 09 删除记忆时，须沿关联回答的 `operation_id` → `memory_recalls.matches` 找到依赖并清理最终缓存及应删除派生内容。原文分段不会接收长期记忆，无须因记忆编辑重新发送全部文档。恢复时比较当前已核验召回材料的指纹；改变则清空最终缓存与已完成调用占位，只重做最终回答，避免重放旧事实。未收尾的旧最终请求仍阻止重叠发送。

## 与搜索的执行顺序

`search.prepare` 是动作回执之后的唯一搜索入口；有明确搜索结果时不进入附件全文处理。没有搜索意图时，普通附件先执行能力门槛，再准备记忆；全文按完成检查点准备所有可读文字。最终调用仍由同一 `BoundCalls` 负责，搜索来源与附件来源分别经过原白名单验证，预算暂停和搜索确认保持各自状态。
