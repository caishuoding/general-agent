# 任务 08：候选记忆及含义不明的变更确认

## 已实现的交互和公开接口

自动候选只存在应用业务状态中。卡片展示准备保存的事实、归属“你”、当前用户消息逐字来源；可能变更时另外展示原目标事实。确认前不写 Mem0，不作为跨会话记忆召回。确认后沿任务 05 的直接保存或任务 07 的稳定标识更新，完整成功才显示“已确认并保存 / 更新”。拒绝不发送云端请求；刷新、重复点击保持同一结果。

- `POST /api/memory-candidates/{id}/confirm`：批准已展示的具体候选。不可通过请求正文替换事实、人物或目标。支持 `X-Operation-ID`；范围绑定候选 ID、事实、目标及版本、嵌入配置修订。预算暂停返回既有 402 协议；同一失败操作重放返回原失败，用户主动重试使用新 operation。
- `POST /api/memory-candidates/{id}/reject`：只拒绝未批准的 pending 候选，可重复执行。已开始正式提交的候选不能伪装为未批准；失败 / 暂停展示重试提交。
- `POST /api/conversations/{conversation}/messages/{user_message}/memory-candidates/retry`：明确重试原用户来源的识别，只读取该会话内的 user 消息。助手标识或不支持的来源返回 409；已完成的发现不再次提取。
- 会话及 SSE 的助手消息新增 `memory_candidates` 和 `memory_discovery`（pending / complete / failed 与安全错误）。同一用户消息的重试回答共享发现检查点和候选身份，不重新插入候选。

首版自动触发使用保守中文个人表达门槛：`我喜欢 / 我偏好 / 我住在 / 我居住在 / 我在 / 我是`、`我的名字 / 昵称 / 职业 / 工作 / 生日 / 语言` 等开头，及 `最近在`。问题、否定、转述、虚构、资料处理、检索和明确记忆动作不走此自动路径。未覆盖的自由表达仍可正常聊天或直接明确要求保存，不宣称能理解全部表达。只向提取模型发送当前获准用户消息，以及按本地属性匹配的最多五条正式目标快照；不发送旧会话、助手文本或附件。模型结果必须有实际当前消息中的来源原文、归属 user、合法目标及不超过五条的具体事实，否则整个结果标为失败，不生成可确认卡片。提取仅建议，卡片上的事实需要用户核对。

例如已有“我住在苏州”，当前表达“最近在杭州”可以提出“我住在杭州”的候选变更，但不会把出差直接当作搬家。卡片绑定目标 ID 与原版本；确认前目标被更正或停用，旧候选失效，不能覆盖较新的事实。候选七天过期，服务端每次读取 / 确认核验。不同候选可来自同一消息并分别批准；正式来源因此是一对多关系。

## 预算、状态和恢复

发现步骤在现有 `ChatExecution.prepare` 中执行，沿同步 `/messages` 与浏览器 `/runs` 的共同执行器。提取和确认嵌入都使用唯一调用网关；不创建独立计费或聊天执行路径。普通个人表达先持久化当前消息，再在实际步骤申请预算。提取成功后检查点记录 complete；后续召回 / 回答暂停跨重启恢复不重复提取。`chat_reservation` 仅复用仍为 reserved 的聊天调用。

提取失败不把普通回答伪装为失败，但在旁边单独显示候选识别失败及明确重试入口。已发请求的返回用量仍计入；停止期间返回的提取结果不创建候选。应用启动把非预算暂停的中断发现、saving 候选提交标为失败，并撤销其后续调用许可。预算暂停保留原步骤；确认的正式保存 / 更正复用既有部分提交核验，重试不重复创建动作或递增版本。

09 的来源失效规则需接入 `MemoryCandidates.source`（当前只核验会话归属、消息存在和 user 角色），并阻止旧 `discover_source` 重试重新提出被删除事实；确认再次核验当前逐字来源和目标版本。候选拒绝本身终结该候选，完成发现不会再次自动生成它。删除已批准记忆本身不等于删除原聊天，这是后续 09 的明确抑制规则。

14 的附件提取需要独立明确授权来源与人物核对；不能把附件文本伪装成当前 user 消息复用自动发现门槛。可共用最终批准 → 05 / 07 的正式动作规则，但必须扩展候选来源类型、核验和卡片，仍受预算控制。16 的历史查询结果只作回答材料，不调用候选发现或升级为保存授权。13 / 17 应保留共同 `prepare(..., settings)`，文档与明确搜索的流程在其后继续；自动候选模块不会调用资料处理或搜索服务。
