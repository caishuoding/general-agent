# 任务 17：明确联网搜索与个人信息外发确认

通过统一 ChatExecution、同步 `/messages` 和后台 `/runs` 接入 Tavily。独立 SearchService 管理持久查询、外发许可、实际结果与来源核验，没有新建平行聊天执行器。保留已合入的 07 记忆更正、11 文档提取与 12 图片能力。

## 配置与用户行为

`GET /api/settings/search` 只返回 API 地址、固定身份 `tavily-basic` 和密钥配置状态；`PUT` 保存，`DELETE` 移除。凭据在 `APP_DATA_DIR/search.json` 原子写入，权限 0600，与聊天和嵌入配置相互独立。同地址空密钥保留已有值，改地址需要新密钥；HTTPS 或回环 HTTP 校验沿用既有安全边界。保存和清除配置都不会请求服务。

当前用户输入以 `联网搜索：具体内容` 或 `请上网查询：具体内容` 等明确句式开头时才联网。否定、引用解释、多行示例和仅讨论联网含义不触发；模型输出、旧消息、网页或附件正文不构成授权。没有配置时明确说明未联网，其他功能仍可用。当前采用保守句式识别，不让模型猜测是否得到用户授权。

直接明确写出的查询按原文发送。需要长期记忆或附件资料时，先通过现有相关召回或会话附件接口取得材料，查询生成模型只能返回 `query` 建议，不能批准它。正式记忆使用真实 Mem0 与业务状态/版本筛选；附件限定本会话已随消息发送的可用资料。图片只有实际参与规划时才要求当前模型修订通过图片能力验证。

所有从记忆或附件得到的查询均显示持久确认卡片，包含完整外发文本、来源名称和“发送到 Tavily 以查询公开网页并回答本次问题”的用途。用户可编辑并保存新 revision、拒绝或批准。准备查询可能已发送材料给用户配置的聊天模型、调用嵌入服务；卡片批准控制的是后续 Tavily 搜索，界面及 README 明确说明这个范围。

`PUT /api/conversations/{conversation_id}/search/{id}` 仅接收当前 revision 与新 query；保存生成新 revision，不外发。`POST .../decision` 仅接收 revision 与 approve/reject，不接受任意客户端状态。批准绑定服务端实际查询、来源标识/版本、会话、服务修订、操作与单次执行，有效期 30 分钟。跨会话、旧 revision、过期、已停止或已拒绝的批准失效。直接恢复暂停消息不能替代外发许可；重复确认不会启动第二次搜索。

来源在批准时及执行/恢复时重新核验。管理页更正记忆导致版本变化后，待确认或已批准但预算暂停的旧查询都会失效；不会继续发送旧地址。配置改变后要求新执行。刷新或应用正常重启保留待确认状态，生成途中重启则撤销操作、标明失败。

## 请求、来源与计量

对照 [Tavily 官方 Search 接口](https://docs.tavily.com/documentation/api-reference/endpoint/search)：服务端使用 Bearer 凭据请求 `/search`，固定 `search_depth=basic`、`topic=general`、`max_results=5`、`include_answer=false`、`include_raw_content=false`、`include_usage=true`、`auto_parameters=false`。超时 30 秒，不跟随重定向；错误只显示安全的失败信息或状态码，不回显服务商原始错误正文。

保留最多五条实际结果，标题和摘录分别限制 500 / 8000 字符，URL 只接受无凭据、无控制字符的 HTTP(S)。服务器分配稳定 W 标记；最终回答只能把本次返回的标记解析成来源链接，未知标记明确替换为未核验。模型漏写引用时显示警示并仍提供实际结果链接供核对；空结果以本地确定回执说明未找到可核验结果，不能照搬模型声称已经查证的文字。网页正文作为不可信参考资料，不能触发新的搜索或批准。链接使用安全的新窗口属性，模型正文不解释为 HTML。

查询嵌入、生成查询、Tavily 请求和最终回答全部走任务 04 调用网关。搜索使用 `unit=credits`，设置页真实提供每 credit 单价。只记录响应实际报告的有效非负 credits，缺失或畸形仍为未知；HTTP 错误有 usage 也保留。预算批准每次只允许下一次云端调用，不能代替个人资料外发确认。

完成结果持久存储，最终回答受预算暂停后，重启恢复不重复搜索。停止立即撤销后续权限、冻结回答，迟到的查询规划不能覆盖取消状态或重新保存派生查询；已经发出的搜索仍记录实际返回 credits；显式重试创建新执行和查询确认。没有隐藏自动重试，不因失败自动再次收费。

## 数据和任务 09 / 15 必须执行的清理合同

迁移 `018_search.sql` 在 PostgreSQL 新增 `search_requests`，包括原用户 message_id、conversation_id、唯一 operation_id、具体 query、revision、search_revision、sources、purpose、expires_at、status、results/error。sources 记录记忆动作 ID/版本或附件 ID/创建版本以及显示名称；results 保存实际网页标题、URL、摘录和 W 键。助手 `messages.web_sources` 另外保存已使用出处。API 响应也可能被既有幂等机制缓存到 `cloud_operations.result`。

以下属于删除功能的必要整合要求，不能作为可选清理：

1. 按被删除记忆/附件的 sources ID 找出所有依赖搜索，并先撤销关联 cloud_operations 的批准和执行，阻止待发请求及后续模型调用。正在外部服务执行的请求不能追溯撤回，返回数据不得重新写回已失效检查点。
2. 清除搜索检查点中的 query、results、sources 显示名称等派生正文与批准，清理对应助手的 web_sources 以及关联 cloud_operations.result 缓存。只保留必要、不含正文的失效标记。不能仅删除原附件/记忆就留下含地址的查询、网页摘录或旧批准。
3. 删除会话时 `search_requests.message_id` 与 conversation_id 有外键，先删搜索记录，再处理消息和会话；撤销与清空所有相关操作缓存后再删除。单独删除来源时，也需处理其他会话中依赖该来源的搜索检查点。
4. 已存在聊天正文遵循原会话保留规则另行处理；删除记忆本身不等于删除原聊天，但派生检查点/批准不能借此保留。记忆源版本失效只是防止再使用，不能替代上述正文清理。

当前来源核验已阻止失效版本继续发送；任务 09 / 15 负责接入实际删除动作与立即清理。原文件、Mem0 正式实体和内部历史清理由各自既有删除合同共同覆盖。
